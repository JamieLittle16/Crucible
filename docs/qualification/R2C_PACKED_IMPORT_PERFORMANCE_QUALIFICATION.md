# R2C Packed Import Performance Qualification

Status: **diagnostic baseline established; word-major unpack candidate rejected; production performance admission still open**  
Target: **Minecraft: Java Edition 26.2 / DataVersion 4903**  
Parent qualification: `R2C_PREGENERATED_WORLD_IMPORT_QUALIFICATION.md`

## Purpose

This document records the performance evidence used to select or reject R2C cold stored-world import mechanisms. It is deliberately separate from semantic admission: a faster mechanism is never accepted unless the existing exact semantic and hostile-input gates remain unchanged.

The current packed fixture is the independent `differential-packed4-gzip` region generated by `tools/r2c_import_differential.py`. It exercises one non-uniform 4096-cell four-bit block-state section through the real stored-chunk transaction.

All numbers in this document are **hosted diagnostic evidence**, not target-hardware production admission. Absolute timings from different GitHub runners must not be compared as if they were one controlled machine. Same-run component comparisons and repeated direction are useful for deciding which mechanism deserves a production experiment.

## Permanent acceptance discipline

A candidate optimization is promoted only when all of the following hold:

1. the candidate has an isolated benchmark or decomposition showing a plausible mechanism-level win;
2. production code remains architecturally clean and adds no timing flags, trait objects, counters, or other HOT-path tax;
3. `cargo check`, Clippy with `-D warnings`, Rust tests, rustfmt, hermetic `--offline --locked` qualification, and repository policy remain green;
4. the independent Python/Rust semantic differential remains identical at every compared block cell;
5. hostile-input behavior and exact error semantics are preserved;
6. the whole packed stored-chunk import improves, not merely the isolated microbenchmark;
7. the uniform path does not materially regress;
8. the result and any rejection are documented before moving to the next mechanism.

A negative result is evidence. We do not retain a more complicated mechanism merely because it looked theoretically attractive.

## Baseline: transparent section-builder decomposition

PR #219 added nested timing around the qualification-only transparent final-section builder. On the hosted run that motivated the next experiment, packed import was approximately:

- total import p50: **36.58 us**;
- transparent section-builder p50: **11.36 us**;
- importer residual p50: **25.22 us**;
- resident install p50: **0.08 us**.

The transparent correctness/reference builder therefore explained only about 31% of packed import latency. It was not valid to optimize or replace that builder simply to make the benchmark number look better.

## Candidate P1: word-major non-spanning packed decode

### Hypothesis

The current production packed-cell loop iterates all 4096 cells and derives the source word and local slot with per-cell division/modulo:

```text
word  = packed_words[cell / values_per_word]
shift = (cell % values_per_word) * bits_per_entry
```

A plausible alternative is to traverse one packed word at a time and repeatedly shift it, avoiding per-cell division/modulo while preserving the same non-spanning 26.2 layout and exact cell-indexed error reporting.

The candidate was intentionally benchmarked before modifying production.

### Probe design

`r2c_packed_unpack_probe` compares:

- the existing cell-major arithmetic shape;
- a word-major shifting shape.

Both paths:

- decode exactly 4096 cells;
- use the same two-state four-bit palette fixture;
- perform checked palette lookup;
- preserve exact cell numbering for out-of-range diagnostics;
- produce an identical semantic checksum;
- reuse preallocated output vectors;
- run in release mode;
- remain `diagnostic_only` and `performance_admitted: false`.

The first 64-round smoke indicated no win: cell-major p50 **5.749 us**, word-major p50 **5.799 us**.

Because the difference was small, the benchmark was strengthened rather than immediately concluding:

- smoke rounds increased from 64 to **1024**;
- warmups increased from 16 to **128**;
- measurement order alternates every round so neither mechanism is systematically first;
- semantic equality and checksum stability remain mandatory.

### Hardened result

Workflow run `33309061607`, job `99250701235`, AMD EPYC 9V74:

| Loop | p50 | p95 | p99 |
| --- | ---: | ---: | ---: |
| current cell-major | **5.729 us** | 5.739 us | 5.749 us |
| word-major candidate | **5.768 us** | 5.829 us | 5.839 us |

The reported p50 ratio was `1006` milli, i.e. the word-major candidate was about **0.7% slower** at p50. The same run preserved the packed semantic checksum and the full independent importer differential passed with SHA-256:

`98cf921d050b0270c305138664d8fadd9fb85966f2e71a9eb7337cc9a4c24b12`

### Decision

**Reject P1. Do not modify production packed decode to word-major traversal.**

The transformation removes visible division/modulo from source but does not improve the compiled loop on the measured hosted target. LLVM can already optimize the fixed arithmetic effectively, and the alternative introduces its own loop/state costs. A source-level operation count is not sufficient evidence.

The existing simpler cell-major loop remains selected until a different candidate demonstrates a real whole-import gain.

## Current next target: decompression

The largest measured packed-import component is now payload decode/decompression, approximately **14.8--16.5 us p50** across the two hosted component runs.

The next experiment should decompose the gzip path without instrumenting production:

1. exact gzip framing/header work;
2. raw `miniz_oxide` DEFLATE inflate into a preinitialized bounded output buffer;
3. Helve-owned gzip CRC32 verification;
4. ISIZE/exact-consumption checks;
5. any retained-buffer/high-water policy cost.

The benchmark should live in qualification/example code and use the import crate's already-pinned `miniz_oxide` dependency. It must compare against the complete production `DeflateChunkPayloadDecoder` on identical bytes and verify identical decompressed output before reporting timings.

Potential optimizations are not selected in advance. In particular, checksum policy, bounds checks, exact-consumption validation and fail-closed malformed-input behavior are semantic/safety requirements and may not be removed for speed.

## Whole-path baseline retained for requalification

On workflow run `33309061607` / job `99250701235`, the same AMD EPYC 9V74 runner reported:

- uniform import p50: **4.407 us**;
- uniform whole import + install p50: **4.617 us**;
- packed import p50: **37.385 us**;
- packed transparent builder p50: **11.747 us**;
- packed importer residual p50: **25.638 us**;
- packed resident install p50: **0.090 us**;
- packed whole import + install p50: **37.465 us**.

These values are diagnostic anchors for that exact run only. Future production candidates should be compared on the same runner/run whenever possible, and final mechanism selection still requires controlled target-hardware evidence.

## Requalification triggers

Re-run the affected performance evidence when any of these change materially:

- gzip/zlib decoder implementation or dependency version/features;
- output-buffer sizing/reuse policy;
- NBT cursor or packed-state decoding;
- persisted-state resolver generation/lookup;
- final-section construction mechanism;
- resident installation transaction;
- packed fixture identity or semantic checksum;
- compiler/toolchain or target CPU for numerical baselines;
- benchmark timing methodology.

## Current non-claims

This evidence does **not** mean:

- the transparent reference builder is the eventual production section representation;
- gzip/zlib performance is production-selected;
- hosted CI timings are a target-hardware throughput guarantee;
- the remaining 9--10 us residual is wholly packed-cell decoding;
- microbenchmark speed can override vanilla semantic parity or hostile-input guarantees.

It does establish that Helve has enough instrumentation-free decomposition to avoid optimizing the wrong layer, and that one plausible packed-loop rewrite was tested rigorously and rejected rather than cargo-culted into production.
