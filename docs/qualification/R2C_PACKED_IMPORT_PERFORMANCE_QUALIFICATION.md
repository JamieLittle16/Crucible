# R2C Packed Import Performance Qualification

Status: **component baselines established; word-major unpack rejected; byte-table gzip CRC selected; post-CRC bottleneck map established; target-hardware performance admission still open**  
Target: **Minecraft: Java Edition 26.2 / DataVersion 4903**  
Parent qualification: `R2C_PREGENERATED_WORLD_IMPORT_QUALIFICATION.md`

## Purpose

This document records the performance evidence used to select or reject R2C cold stored-world import mechanisms. It is deliberately separate from semantic admission: a faster mechanism is never accepted unless the existing exact semantic and hostile-input gates remain unchanged.

The packed fixture is the independent `differential-packed4-gzip` region generated by `tools/r2c_import_differential.py`. It exercises one non-uniform 4096-cell four-bit block-state section through the real stored-chunk transaction.

All numbers here are **hosted diagnostic evidence**, not target-hardware production admission. Absolute timings from different GitHub runners must not be compared as if they were one controlled machine. Same-run component comparisons and repeated direction are used for mechanism selection.

## Permanent acceptance discipline

A candidate optimization is promoted only when all of the following hold:

1. the candidate has an isolated benchmark or decomposition showing a plausible mechanism-level win;
2. production code remains architecturally clean and adds no timing flags, trait objects, counters, or other hot-path tax;
3. `cargo check`, Clippy with `-D warnings`, Rust tests, rustfmt, hermetic `--offline --locked` qualification, and repository policy remain green;
4. the independent Python/Rust semantic differential remains identical at every compared block cell;
5. hostile-input behavior and exact error semantics are preserved;
6. a local microbenchmark win survives in the complete affected production mechanism;
7. the surrounding importer shows the same causal direction without using cross-run hardware noise as evidence;
8. unaffected paths do not materially regress;
9. the result and any rejection are documented before moving to the next mechanism.

A negative result is evidence. Helve does not retain a more complicated mechanism merely because it looked theoretically attractive.

## Baseline: transparent section-builder decomposition

PR #219 added nested timing around the qualification-only transparent final-section builder. On the hosted run that motivated further decomposition, packed import was approximately:

- total import p50: **36.58 us**;
- transparent section-builder p50: **11.36 us**;
- importer residual p50: **25.22 us**;
- resident install p50: **0.08 us**.

The transparent correctness/reference builder therefore explained only about 31% of packed import latency. It was not valid to optimize or replace that builder simply to make the benchmark number look better.

## Candidate P1: word-major non-spanning packed decode

### Hypothesis

The current packed-cell loop derives the source word and local slot per cell:

```text
word  = packed_words[cell / values_per_word]
shift = (cell % values_per_word) * bits_per_entry
```

A word-major traversal could avoid visible per-cell division/modulo while preserving the same non-spanning 26.2 layout and exact cell-indexed error reporting.

### Hardened result

The probe compares the existing cell-major arithmetic shape with a word-major shifting shape. Both decode exactly 4096 cells, perform checked palette lookup, preserve exact cell numbering, reuse preallocated output and require identical semantic checksums.

Workflow `33309061607` / job `99250701235`, AMD EPYC 9V74:

| Loop | p50 | p95 | p99 |
| --- | ---: | ---: | ---: |
| current cell-major | **5.729 us** | 5.739 us | 5.749 us |
| word-major candidate | **5.768 us** | 5.829 us | 5.839 us |

The word-major candidate was about **0.7% slower** at p50. A later EPYC 7763 run (`33309493746` / `99251847080`) again showed no win: cell-major **6.963 us**, word-major **6.973 us**.

### Decision

**Reject P1.** The source-level arithmetic rewrite does not improve the compiled loop on the measured hosts. The simpler cell-major implementation remains selected.

## Candidate P2: 256-entry byte-table CRC32

### Isolated qualification

PR #224 compared the 16-entry nibble table with a compile-time 256-entry byte table using the same reversed polynomial `0xedb8_8320`.

The candidate adds 960 bytes of static table data but no allocation, dependency, unsafe code, dynamic dispatch or runtime initialization.

Workflow `33309850528`, job `99252815161`, AMD EPYC 7763:

| CRC mechanism | p50 |
| --- | ---: |
| 16-entry nibble table | **10.286 us** |
| 256-entry byte table | **5.412 us** |

That is an isolated **47.4% p50 reduction** on the exact 2204-byte decompressed fixture. Measurement uses 1024 rounds, 128 warmups, 64 CRC calls per timed batch and alternating order. Both mechanisms must equal the gzip trailer CRC before measurement.

### Production qualification

PR #225 spliced the exact byte-table recurrence into `compression.rs` and added an explicit FHCRC regression. No other gzip framing, DEFLATE, bounds, exact-consumption, ISIZE, ownership or buffering mechanism changed.

Workflow `33317192460`, job `99272688327`, Intel Xeon 6973P-C:

| Measurement | p50 |
| --- | ---: |
| old-equivalent diagnostic complete gzip decode | **11.967 us** |
| production byte-table complete gzip decode | **7.718 us** |
| nibble CRC probe | **8.038 us** |
| byte-table CRC probe | **4.282 us** |
| production packed payload decode | **7.513 us** |
| production packed import | **21.399 us** |
| production uniform/zlib import | **3.355 us** |

The complete production decoder therefore improves by **4.249 us p50 / 35.5%** on a same-run old-equivalent comparison. The CRC microbenchmark independently repeats a roughly **46.7%** reduction on this second CPU architecture.

The packed importer records exactly one decoder call per chunk, so this complete-decoder reduction is a direct causal reduction inside packed import. The absolute packed import number is not compared against a different hosted runner as though it were a controlled whole-path A/B.

### Semantic closure

The production branch is green through hermetic build/tests, rustfmt, Clippy `-D warnings`, checksum/ISIZE/FHCRC failure regressions, the independent seven-section importer differential, and the existing vanilla-save oracle regressions. The differential digest remains:

`98cf921d050b0270c305138664d8fadd9fb85966f2e71a9eb7337cc9a4c24b12`

The regenerated official 26.2 corpus workflow `33317192512`, job `99272688526`, also completed green through runtime-state identity binding, deterministic official spawn generation, raw-Anvil production comparison, independent normalized-corpus validation, reconstruction through every Rust candidate, parser-admission fail-closed checks, Python/Rust evidence cross-checks and real-target identity verification.

### Decision

**Select P2 for R2C production.** The additional 960 static bytes are justified by the isolated and complete-decoder savings while all semantic gates remain exact.

`performance_admitted` remains false because hosted CI establishes mechanism selection, not a controlled target-hardware throughput guarantee.

## Post-CRC bottleneck map

The byte-table CRC materially changes what is worth optimizing next. On the same Intel Xeon 6973P-C production-selection run, the packed component diagnostic reported:

| Component | p50 |
| --- | ---: |
| total packed import | **22.353 us** |
| payload decode | **7.513 us** |
| block-state resolve | **0.097 us** |
| transparent/reference section build | **8.115 us** |
| residual NBT / packed-cell / transaction work | **6.618 us** |

The same run's isolated packed-loop probe reported cell-major **4.010 us** and word-major **4.013 us**, again confirming that word-major traversal is not the answer.

The next optimization target must therefore be selected carefully:

- **do not** optimize state resolution; it is already negligible;
- **do not** replace the transparent/reference builder merely to improve a qualification number unless the R2C architecture is explicitly ready to select a production section-construction mechanism;
- decompression is no longer dominated by CRC, so further gzip work must separately justify itself;
- the remaining **6.6 us** residual should be decomposed before changing NBT or packed-cell production code;
- if/when a Helve-native production section builder is introduced, benchmark it against the transparent reference while requiring identical section semantics.

The most conservative next performance experiment is to split the residual into schema-directed NBT cursor work, packed long-array ingestion/unpack, and transaction/framing overhead using qualification-only wrappers or equivalent static seams. That avoids prematurely optimizing the reference builder or guessing that all residual time belongs to packed-cell arithmetic.

## Requalification triggers

Re-run affected evidence when any of these change materially:

- gzip/zlib decoder implementation or dependency version/features;
- CRC32 implementation or table shape;
- output-buffer sizing/reuse policy;
- NBT cursor or packed-state decoding;
- persisted-state resolver generation/lookup;
- final-section construction mechanism;
- resident installation transaction;
- packed fixture identity or semantic checksum;
- compiler/toolchain or target CPU for numerical baselines;
- benchmark timing methodology.

## Current non-claims

This evidence does **not** mean:

- the transparent reference builder is the eventual production section representation;
- the selected CRC table proves the rest of gzip/DEFLATE is globally optimal;
- hosted CI timings are a target-hardware throughput guarantee;
- the remaining residual is wholly packed-cell decoding;
- CRC verification may be weakened or removed;
- a larger slicing-by-N CRC table would necessarily improve whole import;
- microbenchmark speed can override vanilla semantic parity or hostile-input guarantees.

It does establish a disciplined sequence: the importer was decomposed, a plausible packed-loop rewrite was rejected, the actual gzip bottleneck was localized, a CRC candidate was isolated before production, the complete decoder improvement was then measured, and semantic closure was re-proved against both synthetic and regenerated official-world evidence.
